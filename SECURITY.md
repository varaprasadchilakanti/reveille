# Security Policy

## Supported Versions

Only the current stable release receives security fixes.

| Version | Supported |
|---------|-----------|
| 0.9.x   | Yes       |
| < 0.9.0 | No        |

## Reporting a Vulnerability

Do not open a public GitHub issue for security vulnerabilities.

Use GitHub's private vulnerability reporting:
[Report a vulnerability](https://github.com/varaprasadchilakanti/reveille/security/advisories/new)

Include a description of the vulnerability and its potential impact,
steps to reproduce it, and the version of Reveille and Python in use.

Reveille has one maintainer and no on-call rota. Reports are normally
acknowledged within a few days; no response time is guaranteed.

## Release Integrity

Reveille is published to PyPI only by the tagged `Publish` workflow in
this repository. There are no stored PyPI credentials to steal: the
workflow authenticates as a
[Trusted Publisher](https://docs.pypi.org/trusted-publishers/) over
OIDC, and the token it receives is minted per run and scoped to this
project.

Every GitHub Action used here is pinned to an immutable commit SHA, with a comment naming the
version it resolves to. A test asserts both, so an action reintroduced by a mutable tag fails CI.

### Attestations

Distributions published from v0.7.0 onward carry
[PEP 740](https://peps.python.org/pep-0740/) digital attestations. These
are generated by `pypa/gh-action-pypi-publish`, which produces them by
default and is pinned here at v1.14.2.

An attestation binds a distribution file's hash to the identity that
published it, so it answers a question a checksum cannot: not merely
"was this file altered", but "did this file come from this repository's
release workflow".

To verify a distribution against this repository:

```console
$ pip install pypi-attestations
$ pypi-attestations verify pypi \
    --repository https://github.com/varaprasadchilakanti/reveille \
    <direct URL of the file on files.pythonhosted.org>
```

The command downloads the file and its provenance through PyPI's Integrity API and checks that the
Trusted Publisher identity matches the repository given. The `pypi-attestations` CLI describes
itself as experimental and not a stable interface; the attestations are a published standard.

### Software Bill of Materials

Each tagged release generates a
[CycloneDX](https://cyclonedx.org/) 1.6 SBOM in JSON, covering the
runtime dependency graph resolved from `poetry.lock`. Development and
test dependencies are excluded: they describe how Reveille is built, not
what an installation of it contains.

The SBOM is produced by a job independent of publishing, so a failure to generate one cannot
withhold a release. It is uploaded as the `sbom` artifact of the workflow run and attached to the
GitHub Release with its Sigstore attestation bundle (`<sbom filename>.sigstore.json`). The bundle
is the attestation the workflow also writes to GitHub's attestation store, so the SBOM can be
verified from the two files alone:

```console
$ gh attestation verify reveille-X.Y.Z-sbom.cdx.json \
    --bundle reveille-X.Y.Z-sbom.cdx.json.sigstore.json \
    --repo varaprasadchilakanti/reveille \
    --predicate-type https://cyclonedx.org/bom
```

`--predicate-type` is not optional here: the flag defaults to SLSA
provenance, and this attestation is a CycloneDX one.

Releases from v0.8.1 and earlier carry no such bundle; the attestation
for those exists in the attestation store and is reachable with the same
command minus `--bundle`.

The workflow drafts the Release with both files attached; it is a draft because a published
release accepts no assets once release immutability is enabled. **v0.8.0 has no SBOM attached to
its Release**, because the attesting step failed on a glob it could not expand; its `sbom`
workflow artifact and the regeneration path both work. Regenerate from a checkout at any tag:

```console
$ make sbom
```

The output is byte-reproducible for a given `poetry.lock`, so it can be compared directly against
a published one.

## Project Posture

[![OpenSSF Scorecard](https://api.scorecard.dev/projects/github.com/varaprasadchilakanti/reveille/badge)](https://scorecard.dev/viewer/?uri=github.com/varaprasadchilakanti/reveille)

The Scorecard score above is live and is a composite. Reveille has a **single maintainer**, so
two checks cannot honestly be satisfied.

**Code review.** Scorecard's Code-Review check looks for a second person's approval. There is
none, and GitHub forbids approving your own pull request, so a review requirement would block
every merge or need a bypass that records an approval that did not happen. The alert is dismissed
deliberately. What partly compensates, and does not substitute:

- Every change reaches `main` through a pull request with required status checks.
- CodeQL runs on every pull request with the `security-extended` query set.
- Every GitHub Action is pinned to a commit SHA, and a test fails the build if that lapses.
- Publishing is by Trusted Publisher over OIDC with PEP 740 attestations.
- Architectural properties are asserted by tests, not review habit: layering, action pinning,
  lock-file validity, licence consistency, and agreement between the capability document and the
  program it describes.

**Fuzzing.** Scorecard's Fuzzing check credits OSS-Fuzz membership, ClusterFuzzLite, or a harness
in a language it recognises: Go, Haskell, JavaScript and TypeScript, Erlang, C# and F#. Python is
not among them. Fuzzing would be worthwhile here and has not been done: Reveille parses untrusted input (author names, addresses
and `.mailmap` contents from an arbitrary repository) and renders it into HTML and CSV, and an
adversarial review of v0.8.0 found five real issues in that surface.

## Threat Model

The case that matters is **a user running Reveille against a repository somebody
else controls** — a clone, a fork, a pull-request branch. Everything in git
history is then attacker-supplied text: author names, email addresses,
`.mailmap` contents, and ref names. So is any `reveille.toml` at the repository
root, because the CLI discovers that file automatically from the working
directory, and its values reach the same places the flags do.

v0.8.0 closed five issues found under that model, each reproduced against a real
malicious repository before being fixed: argument injection into `git log` that
allowed arbitrary file overwrite, CSV formula injection, contributor forgery
through separator injection into author fields, an output-path validation bypass
combined with symlink-following writes, and an unhandled crash on a forged
timestamp. Regression tests for all five live in
`tests/integration/test_security.py`, and each was observed failing against the
reintroduced vulnerability before being trusted.

v0.9.0 closed eleven more, each with a test observed failing before the fix:

- A token in the remote URL (`https://user:token@host/...`) was printed in the
  HTML report and the JSON. Credentials, query string and fragment are now
  removed.
- A `reveille.toml` could set the output path to `.git/HEAD`, which overwrote it
  and left a clone Git could not read. Any output path inside `.git` is now
  refused, and a discovered `reveille.toml` prints the settings it applied.
- Names and addresses from `.mailmap` skipped the scrubbing and length limits
  applied to author fields, a symlinked `.mailmap` was followed, and a
  non-UTF-8 one crashed the run.
- Four escapes in the report had no test, so any one could have been removed
  unnoticed. Each now has one.
- A direction override in a name made it display as text it does not contain
  (`\u202eevil\u202c Name` read "live Name"). Direction overrides and
  isolates, zero-width spaces and byte-order marks are removed from names.
- Values from a `reveille.toml` reached stderr with their terminal control
  sequences intact, so a file could erase the warning about itself. Every
  message and warning Reveille prints now shows them as escapes.
- A partial clone (`git clone --filter`) made Git fetch the missing objects
  from the remote and write them into `.git/objects` during analysis. Such a
  clone is now refused with exit 2.
- A replace ref or a `.git/info/grafts` file could substitute history, so the
  report named an author the recorded commit did not have. Neither is
  followed; their presence is stated.
- `log.showSignature` in a repository's own `.git/config` made every command
  run the `gpg.program` that file names, on a commit carrying a signature
  header. Every read pins it off.
- A commit whose author field carried the record separator was dropped from
  every figure without a word. It is now counted and stated.
- `--exclude-author` by one name left the same person in the report under
  another name. Every commit under an address the value reached, anywhere in
  the branch's history, is now removed.

A red-team pass on 2026-10-12 found five more, fixed for the next release, each
with a test observed failing before the fix:

- A `.mailmap` could stall a run for minutes: its line patterns backtracked
  quadratically, and the working-tree file had no size bound. Lines are parsed
  in one pass and the file is bounded at 1 MiB.
- A report path hard-linked to `.git/HEAD` was written through, and `--output`
  could name the HEAD of the repository a linked worktree belongs to. Reports
  are written to a new file and moved into place, and a worktree's common Git
  directory is refused.
- A file extension could put a clickable link into a chart, and `<!--<script`
  in a path, extension or name blanked every chart. In our tests, no script
  ran in either case.
- `summary` and `who-changed` printed control characters from a directory name
  or a `.mailmap` name on stdout.
- A token in a transport-prefixed remote (`https::https://TOKEN@host/...`) was
  printed.

Verified unaffected, by testing: script execution from repository text, the
report's loading of remote resources, and the CI workflows. The tool's own
offline guarantee was affected: see the partial-clone entry above.

**One limit, stated plainly.** Git honours the configuration in a repository's
own `.git/config`, and some settings name a program for Git to run. Reveille
switches off the ones its reads were measured to start, each proven by a test
that watches the program not run: `gpg.program` (`log.showSignature`), a
`core.fsmonitor` program, and, for `reveille state`, the content filters
(`clean`, `smudge`, `process`) the repository's own config defines. Its history
reads were measured not to start a `textconv` driver. Git has many settings,
though, and Reveille cannot rule out every one, so analysing a repository whose
`.git` directory came from someone else may still run what that file names. `git clone` does not copy `.git/config`; a copied directory, an
archive or a shared drive does. Treat such a repository as you would any
untrusted code.

## Scope

Reveille is a local analysis tool. It reads only the Git repository
it is explicitly pointed at, writes one output file (HTML, JSON or
CSV), and does not transmit data over a network. It does not accept inbound
connections and does not execute content from commit messages or file
contents. Git, which Reveille runs, obeys the repository's own `.git/config`
(see Threat Model above). The primary attack surface is maliciously crafted Git
repository content that could affect the HTML output, or
vulnerabilities in the runtime dependency chain (GitPython, Jinja2,
Plotly, Typer).
